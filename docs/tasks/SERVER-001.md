# SERVER-001 — Первый gRPC-сервер

## Статус

В работе. RPC-контракт добавлен, зависимости закреплены, генерация C++ API
настроена, обработчик `SubmitTelemetry` реализован, собирается на Windows/MSVC и
покрыт модульными тестами. Следующий шаг — запускаемый процесс и сетевой
интеграционный тест.

## Цель

Создать минимальный синхронный gRPC-сервер для Ubuntu/Linux, который принимает
одно protobuf-событие телеметрии, преобразует его в доменную модель и возвращает
успех либо корректную gRPC-ошибку.

Этап должен доказать полный путь от сетевого контракта до проверенной модели, но
не должен добавлять хранение, авторизацию или настоящий сбор метрик.

```text
gRPC request
    ↓
guardian::v1::TelemetryEvent
    ↓ from_proto()
guardian::model::TelemetryEvent
    ↓
accept или INVALID_ARGUMENT
```

## Предлагаемый RPC-контракт

Добавить `proto/guardian/v1/telemetry_service.proto`:

```proto
syntax = "proto3";

package guardian.v1;

import "guardian/v1/telemetry.proto";

message SubmitTelemetryResponse {
  string event_id = 1;
}

service TelemetryService {
  rpc SubmitTelemetry(TelemetryEvent) returns (SubmitTelemetryResponse);
}
```

При успешном запросе сервер возвращает `grpc::Status::OK` и ID принятого события.
Если `from_proto()` отклоняет сообщение, сервер возвращает статус
`INVALID_ARGUMENT`. Текст ошибки не должен содержать чувствительные данные.

## Зависимости и CMake

- использовать gRPC `v1.83.0` и его штатный Protobuf `v35.1`;
- не загружать и не собирать вторую независимую копию Protobuf;
- отключить тесты и примеры стороннего проекта;
- генерировать `.grpc.pb.h/.cc` только в build-каталоге;
- создать target с alias `Guardian::Rpc`, публикующий сгенерированный сервисный
  API;
- связать `guardian-server` с `Guardian::Rpc` и `Guardian::Proto`;
- не использовать глобальные `include_directories()` и `link_libraries()`.

Решение по зависимостям:

- gRPC `v1.83.0` загружается через CMake `FetchContent` по неизменяемой метке;
- используется Protobuf `v35.1` из git submodule этого выпуска gRPC, поэтому
  второй экземпляр Protobuf не загружается и не линкуется;
- загружаются только необходимые submodules Abseil, BoringSSL, c-ares,
  Protobuf, RE2 и zlib;
- тесты gRPC и плагины для других языков отключены, включён только
  `grpc_cpp_plugin`;
- сгенерированные `.pb.*` и `.grpc.pb.*` остаются в build-каталоге;
- цель `Guardian::Rpc` публикует сервисный API и транзитивно подключает
  protobuf-сообщения и gRPC C++; `Guardian::Proto` остаётся отдельной целью с
  преобразованиями доменной модели и будет подключена непосредственно сервером.
- логика обработчика оформлена отдельной целью `Guardian::ServerService`, которая
  собирается на Windows и Linux; исполняемый `guardian-server` создаётся только
  на целевой серверной платформе.

## Серверная реализация

Создать класс реализации сервиса, наследующийся от сгенерированного
`guardian::v1::TelemetryService::Service`.

Метод `SubmitTelemetry` должен:

1. проверить ненулевые указатели запроса и ответа;
2. вызвать `guardian::proto::from_proto()`;
3. вернуть `INVALID_ARGUMENT`, если сообщение некорректно;
4. для корректного события записать его ID в ответ;
5. вывести краткую диагностическую запись без полного содержимого события;
6. вернуть `grpc::Status::OK`.

Первый сервер использует синхронный API gRPC. Асинхронный и callback API пока не
нужны: они усложнят обучение, не добавляя ценности первому вертикальному срезу.

## Запуск

- адрес по умолчанию: `127.0.0.1:50051`;
- сервер не должен слушать внешний сетевой интерфейс по умолчанию;
- адрес можно переопределить аргументом командной строки;
- `--help` и `--version` завершают процесс без запуска бесконечного ожидания;
- ошибка создания или привязки сервера приводит к ненулевому exit code.

## Тесты

Обязательные автоматические проверки:

1. корректное CPU-сообщение принимается;
2. корректное memory-сообщение принимается;
3. ID принятого события возвращается клиенту;
4. сообщение без payload возвращает `INVALID_ARGUMENT`;
5. сообщение с пустыми ID отклоняется;
6. сообщение с некорректной метрикой отклоняется;
7. `--version` печатает версию и завершается;
8. существующие тесты модели и Protobuf остаются зелёными.

Логику сервиса следует тестировать без постоянного процесса. Хотя бы один
интеграционный тест должен поднять сервер на loopback с автоматически выбранным
свободным портом, выполнить настоящий RPC и корректно остановить сервер.

Текущий модульный тест напрямую вызывает `SubmitTelemetry` и проверяет успешные
CPU/RAM-запросы, возвращаемый event ID, отсутствие payload, пустые идентификаторы,
некорректные метрики и нулевые аргументы. Проверка реального сетевого пути будет
добавлена вместе с запуском сервера.

## Критерии готовности

- версии всех зависимостей закреплены;
- сгенерированные файлы отсутствуют в Git;
- сервер собирается на Ubuntu с GCC 11 или новее;
- настоящий unary RPC проходит через сетевой стек gRPC;
- сервер принимает корректную телеметрию и отклоняет некорректную;
- процесс можно штатно запустить и остановить;
- все тесты проходят без обращения к внешней сети;
- документация содержит команды сборки и локального запуска.

## Не входит в задачу

- Windows-клиент;
- сбор реальных метрик;
- база данных и очередь сообщений;
- TLS, токены и аутентификация;
- публичное прослушивание внешнего интерфейса;
- streaming RPC;
- retry, балансировка и service discovery;
- production-развёртывание.
