# Дорожная карта до Windows MVP v0.1

## Текущая точка

Рабочий вертикальный путь уже существует:

```text
Windows CPU/RAM → Agent → Protobuf/gRPC → server
                       └→ Named Pipe → Qt/QML dashboard
```

`WIN-003` добавил периодический Agent, а `GUI-001` — первый локальный экран.
`IPC-001` убрал дублирующий WinAPI-сбор из GUI: Qt-клиент асинхронно получает
snapshot от Agent и восстанавливает соединение после перезапуска. Следующий
продуктовый шаг — постоянная идентичность устройства и конфигурация.

Первый GUI-прототип и полный Windows MVP v0.1 — разные рубежи. Окно с двумя
метриками демонстрирует технологию, но ещё не выполняет обещание продукта
`обнаружить → объяснить → порекомендовать`.

## Оставшиеся этапы

Ниже продуктовая последовательность. Перед началом каждого пункта создаётся
отдельное подробное ТЗ; границы могут уточняться после результатов предыдущего.

### 1. GUI-001 verification — установка Qt и визуальная приёмка (выполнено)

- установить Qt 6.5+ для MSVC 2022: Quick, Quick Controls 2, Concurrent;
- собрать `guardian-desktop`;
- проверить русский текст, DPI 100/125/150%, resize и отсутствие зависаний;
- подготовить скриншот эталонного состояния.

Проверено на Windows с Qt 6.8.3/MSVC 2022: target собирается, `qmllint` не
выдаёт предупреждений, окно запускается и автоматически обновляет CPU/RAM.

### 2. IPC-001 — локальная граница Agent ↔ Desktop (выполнено)

- убрать прямой сбор WinAPI из процесса GUI;
- Agent остаётся владельцем collectors;
- GUI получает последние метрики через локальный IPC;
- определить reconnect и состояние «Agent недоступен»;
- закрыть доступ к IPC для посторонних локальных процессов.

После этого GUI и фоновый Agent становятся двумя настоящими компонентами одного
приложения, а не двумя независимыми сборщиками.

Проверено на Windows/MSVC интеграционными тестами: полный и частичный snapshot,
несколько запросов в соединении, ошибочный frame, disconnect и reconnect.

### 3. DEVICE-001 — постоянная идентичность и конфигурация

- стабильный случайный device ID между запусками;
- локальный конфигурационный файл;
- адрес сервера и интервалы без перекомпиляции;
- безопасная запись и восстановление повреждённой конфигурации;
- без аппаратного fingerprinting.

### 4. STORE-001 — SQLite и offline queue

- локальная история метрик;
- ограничение размера и retention;
- очередь неотправленных событий при недоступном сервере;
- повторная отправка без дублирования;
- миграции схемы SQLite.

### 5. COLLECT-001 — процессы, диск и базовые изменения системы

- список процессов и основные потребители CPU/RAM;
- общая активность диска;
- снимок версий ОС и драйверов;
- модель событий расширяется без нарушения совместимости protobuf;
- разные частоты лёгкого и глубокого сбора.

### 6. COLLECT-002 — GPU, VRAM и температуры

- выбрать поддерживаемые Windows API/vendor SDK;
- загрузка GPU и VRAM;
- температуры CPU/GPU там, где источник надёжен;
- явно отображать «недоступно», а не выдумывать нулевое значение;
- проверить NVIDIA, AMD и Intel на доступном оборудовании.

### 7. DIAG-001 — Findings и первые правила диагностики

- отдельная модель `Finding` с severity, evidence и confidence;
- правила высокой CPU/RAM/дисковой нагрузки и температур;
- защита от тревоги по одному случайному пику;
- объяснение, какие измерения породили finding;
- первые экраны «Проверить компьютер» и результата проверки.

Это первый важный рубеж: продукт начинает не просто показывать цифры, а находить
понятную проблему.

### 8. GUIDE-001 — безопасные рекомендации

- связать findings с приоритетными действиями;
- описывать эффект и риск действия;
- только `DETECT → EXPLAIN → RECOMMEND`;
- никаких автоматических опасных исправлений;
- ссылки на системные настройки и проверка результата после действия.

После `DIAG-001 + GUIDE-001` появляется первый законченный сценарий MVP.

### 9. HISTORY-001 — история изменений системы

- изменения драйверов, процессов и ключевой конфигурации;
- временная линия рядом с деградацией производительности;
- ответ на вопрос «что изменилось с момента, когда всё работало»;
- фильтрация шума и сроки хранения.

### 10. GAME-001 — анализ игровой сессии

- обнаружение начала и конца поддерживаемой игры;
- FPS, 1% low и frametime;
- синхронизация CPU/GPU/RAM/VRAM/temperature со spikes;
- итоговый отчёт с вероятными причинами;
- проверить юридические и технические условия выбранного источника FPS.

### 11. SERVER-002 — серверное хранение и выдача результатов

- PostgreSQL-схема пользователей, устройств, событий и findings;
- idempotency по event ID;
- retention и индексы;
- API выдачи последнего состояния, истории и результатов диагностики;
- миграции и резервное копирование.

### 12. DEPLOY-001 — Docker-образ Linux-сервера

Подробное ТЗ уже существует: воспроизводимый Linux-контейнер, healthcheck,
конфигурация через окружение и минимальный runtime image.

### 13. SEC-001 — TLS и аутентификация устройств

- публичный порт только через защищённое соединение;
- регистрация и отзыв credentials устройства;
- rate limits и ограничения размера сообщений;
- секреты не хранятся в репозитории или клиентском `.env` открытым текстом.

### 14. CLOUD-001 — Timeweb Cloud

- домен, DNS, firewall и резервное копирование;
- развёртывание Docker-образа;
- мониторинг, логи и алерты;
- контрольная отправка с внешнего Windows-клиента.

### 15. AI-001 — OpenRouter и доверенные модели

- server-side API key;
- allowlist семейств Claude Sonnet/Opus и GPT-5.6 Sol;
- режимы «дешёвый / баланс / точный» после измерения качества и стоимости;
- AI получает структурированные findings и evidence, а не сырую бесконечную
  телеметрию;
- лимиты токенов, таймауты, fallback и аудит расходов.

### 16. GUI-002 — диагностика, история и контекстный чат

- экран запуска диагностики;
- findings с доказательствами и рекомендациями;
- история системных изменений;
- отчёт игровой сессии;
- AI-чат, привязанный к текущему диагностическому контексту;
- настройки приватности и отправляемых данных.

### 17. SERVICE-001 — Windows Service, tray и установщик

- Agent запускается без открытой консоли;
- штатное обновление и удаление;
- tray показывает состояние Agent/Server;
- Qt runtime разворачивается вместе с приложением;
- Windows Defender/SmartScreen и code signing учитываются в релизном процессе.

### 18. QA-001 — MVP hardening и внешний тест

- Windows 11 primary и Windows 10 22H2 compatibility;
- длительный soak test Agent;
- проверка памяти, CPU overhead и offline queue;
- security review и негативные сетевые тесты;
- privacy policy, журнал согласий и удаление данных;
- сборка версии `0.1.0` для ограниченной группы тестировщиков.

### 19. BILLING-001 — рублёвые AI-кредиты

Коммерческий слой можно проектировать параллельно, но включать оплату до
стабильного измерения себестоимости AI-запросов нельзя. Нужны рублёвые пополнения,
ledger, чеки/юридическая модель, резерв на комиссии и защита от отрицательной
маржи.

## Контрольные рубежи

1. **GUI prototype** — `GUI-001` собран и визуально проверен.
2. **Diagnostic vertical slice** — `DIAG-001 + GUIDE-001`: одна проблема проходит
   путь от метрики до понятной рекомендации в GUI.
3. **Friends alpha `0.1.0-alpha.1`** — локальная сборка, которую можно отправить
   знакомым без облака и оплаты. До неё осталось шесть сокращённых этапов:
   `DEVICE-001`, alpha-срез `COLLECT-001`, `DIAG-001`, `GUIDE-001`, alpha-срез
   `GUI-002` и `ALPHA-001` с упаковкой и smoke-тестами.
4. **Connected alpha** — TLS + Timeweb + серверное хранение + внешний клиент.
5. **AI alpha** — контекстный чат объясняет findings с контролем стоимости.
6. **Windows MVP v0.1** — установщик, ключевые collectors, game session,
   history, diagnostics, guidance, AI и hardening готовы для внешнего теста.

`ALPHA-001` не является полным релизным установщиком. Его задача — собрать Agent,
Desktop и Qt runtime в понятный тестовый пакет, добавить запуск/остановку,
инструкцию, версию и безопасный сбор логов. Timeweb, OpenRouter, биллинг, GPU,
история и игровая аналитика не блокируют этот ранний тест.

Точную календарную дату можно назвать только после оценки этапов и реального
темпа. По текущему объёму до полного замороженного MVP остаётся много крупных
задач; ближайшая полезная цель — не «закончить всё», а собрать GUI и затем закрыть
один настоящий сценарий `обнаружить → объяснить → порекомендовать`.

## Порядок принятия этапов

Перед каждым следующим этапом помощник:

1. пишет подробное ТЗ на русском;
2. объясняет новые API и учебную цель;
3. спрашивает, кто реализует этап — пользователь или помощник;
4. не начинает менять код без ответа на этот вопрос.

Исключение — когда пользователь заранее прямо поручил конкретный следующий этап,
как в случае с `GUI-001`.
