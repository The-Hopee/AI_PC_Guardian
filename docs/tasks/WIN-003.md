# WIN-003 — Периодический цикл телеметрии

## Статус

Реализована на Windows/MSVC. Основной `TelemetryRunner` написан пользователем и
доведён при ревью: добавлены валидация, CLI-интеграция, периодический режим,
`--once`, `--interval-ms`, штатная остановка и loopback-тест.

Тест проверяет полный цикл с настоящими Windows collectors и локальным gRPC-
сервером, частичный отказ CPU RPC и продолжение отправки RAM. Отдельная подмена
collectors через интерфейсы пока не добавлена и остаётся улучшением тестируемости.

Автоматическая проверка: 12 из 12 CTest-тестов пройдены. Ручная приёмка выполнена
для `--once` и периодического режима с интервалом 600 мс; сервер принял все пары,
а Agent завершился по `Ctrl+C` через отзывчивый stop-флаг.

## Зачем нужен этап

Одно измерение доказывает работу WinAPI и gRPC, но ещё не похоже на настоящий
агент. Диагностика и графики требуют последовательности измерений во времени.
Этот этап создаёт такую последовательность без Windows Service, базы данных и GUI.

```text
start
  ↓
collect CPU/RAM → send two events → wait interval
       ↑                               ↓
       └────────── until stop ─────────┘
                         ↓
                    clean shutdown
```

## Цель

Создать тестируемый цикл, который с настраиваемым интервалом собирает CPU/RAM,
отправляет события через существующий `TelemetryClient`, переживает временную
ошибку одного цикла и штатно завершается по запросу пользователя.

## Границы

В рамках задачи `guardian-agent` остаётся обычным консольным процессом. Его можно
запустить вручную и остановить `Ctrl+C`. Регистрация Windows Service, автозапуск,
SQLite, GUI и удалённое управление выполняются отдельными этапами.

## Предлагаемая структура

```text
agent/include/guardian/agent/telemetry_runner.hpp
agent/src/telemetry_runner.cpp
tests/agent/telemetry_runner_test.cpp
```

Сборщик WinAPI и gRPC-клиент уже разделены. `TelemetryRunner` координирует их, но
не должен содержать код `GetSystemTimes`, protobuf-конвертацию или детали gRPC.

## Публичный контракт

Предлагаемый минимальный интерфейс:

```cpp
namespace guardian::agent {

struct RunnerOptions {
    std::chrono::milliseconds collection_interval{5000};
    std::chrono::milliseconds cpu_sample_interval{500};
    std::chrono::milliseconds request_timeout{3000};
};

struct CycleResult {
    bool cpu_submitted;
    bool memory_submitted;
    std::string error_message;
};

class TelemetryRunner {
public:
    TelemetryRunner(TelemetryClient& client, RunnerOptions options);

    [[nodiscard]] CycleResult run_once();
    void run(const std::atomic_bool& stop_requested);
};

}  // namespace guardian::agent
```

Финальные имена можно уточнить при реализации. Важно сохранить разделение:
`run_once()` выполняет один тестируемый цикл, а `run()` отвечает только за
повторение, ожидание и остановку.

## Правила цикла

1. Собрать CPU с заданным `cpu_sample_interval`.
2. Собрать RAM.
3. Создать два события с общим постоянным для процесса `device_id` и разными ID.
4. Отправить оба события с `request_timeout`.
5. Не прекращать попытку отправки RAM, если отправка CPU не удалась.
6. Вернуть результат обеих операций и понятное сообщение об ошибке.
7. Между циклами ждать `collection_interval`.
8. Останавливаться по флагу, выставленному обработчиком `SIGINT`/`SIGTERM`.

## Интервалы и ожидание

- `collection_interval` должен быть положительным;
- `cpu_sample_interval` должен быть положительным и меньше либо равен интервалу
  сбора;
- `request_timeout` должен быть положительным;
- значения CLI по умолчанию: сбор раз в 5 секунд, CPU sample 500 мс, RPC 3 секунды;
- ожидание остановки не должно безусловно блокировать поток на все 5 секунд.

Для отзывчивой остановки допустим короткий sleep с повторной проверкой флага или
`std::condition_variable`. Выбор нужно объяснить при реализации.

## CLI

Добавить параметры:

```text
--interval-ms <positive integer>
--once
```

- без `--once` агент работает до `Ctrl+C`;
- с `--once` выполняет один цикл и завершается — это сохраняет удобную ручную
  проверку текущего поведения;
- неверные и отсутствующие значения завершают процесс кодом `2` и показывают
  usage;
- ошибка отдельного цикла логируется, но в постоянном режиме следующий цикл
  всё равно выполняется;
- в режиме `--once` неуспешный цикл возвращает код `1`.

## Тестируемость

Прямые WinAPI и gRPC-вызовы нельзя удобно воспроизводить во всех сценариях.
Поэтому `TelemetryRunner` должен получать зависимости через небольшие интерфейсы
или функции: источник метрик, отправитель событий, часы/ожидание. Не нужно строить
большой DI-фреймворк — достаточно минимальных C++-интерфейсов для подмены в тесте.

## Обязательные тесты

1. Успешный `run_once()` создаёт и отправляет CPU и memory события.
2. Оба события имеют общий device ID и разные непустые event ID.
3. Payload каждого события имеет правильный тип и значение.
4. Ошибка сбора CPU не мешает попытке собрать и отправить RAM.
5. Ошибка отправки CPU не мешает отправке RAM.
6. Некорректные интервалы отклоняются до запуска цикла.
7. Цикл выполняется повторно, пока stop-флаг не установлен.
8. После установки stop-флага цикл завершается за ограниченное время.
9. CLI `--once` сохраняет успешную ручную отправку двух настоящих событий.
10. Все существующие 11 CTest-тестов остаются зелёными.

Тесты логики не должны реально ждать секунды: ожидание подменяется тестовой
реализацией или используются короткие контролируемые интервалы.

## Ручная приёмка

1. Запустить `guardian-server`.
2. Запустить `guardian-agent --interval-ms 2000`.
3. Увидеть минимум три пары принятых CPU/RAM событий.
4. Остановить агент через `Ctrl+C`.
5. Убедиться, что процесс завершился штатно и не отправил новое событие после
   запроса остановки.
6. Повторить с `guardian-agent --once` и получить ровно одну пару событий.

## Критерии готовности

- агент работает периодически, а не завершается после первого снимка;
- остановка не требует принудительного завершения процесса;
- временный сбой не убивает постоянный режим;
- логика одного цикла тестируется без настоящего сервера и длинных ожиданий;
- CLI валидирует параметры;
- README и статус задачи обновлены;
- сборка и полный CTest проходят на Windows/MSVC.

## Не входит в задачу

- Windows Service и автозапуск;
- постоянный device ID между запусками;
- очередь повторной отправки и offline buffer;
- SQLite/PostgreSQL;
- GUI и IPC;
- GPU, диск, процессы, температуры и игровые метрики;
- TLS и аутентификация.
