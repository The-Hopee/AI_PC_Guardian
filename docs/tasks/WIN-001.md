# WIN-001 — Первый Windows gRPC-клиент

## Статус

Запланирована. К реализации можно переходить после `SERVER-001`: сетевой контракт
и сервер уже готовы, поэтому следующий вертикальный срез должен впервые отправить
событие из процесса `guardian-agent` в `guardian-server`.

## Цель

Превратить текущий демонстрационный `guardian-agent` в однократный Windows-клиент,
который создаёт тестовое событие CPU в доменной модели, преобразует его в
Protobuf, вызывает `TelemetryService.SubmitTelemetry` через gRPC и показывает
результат пользователю.

На этом этапе метрика остаётся синтетической. Получение настоящей загрузки CPU и
памяти через Windows API относится к `WIN-002`.

```text
guardian::model::TelemetryEvent
    ↓ validate + to_proto()
guardian::v1::TelemetryEvent
    ↓ generated gRPC stub
guardian-server
    ↓ SubmitTelemetryResponse
accepted event_id или понятная ошибка
```

## Что нужно понять на этапе

- `grpc::Channel` хранит настройки соединения с адресом сервера;
- сгенерированный `TelemetryService::Stub` предоставляет клиентский метод
  `SubmitTelemetry`;
- `grpc::ClientContext` относится к одному RPC и хранит deadline и метаданные;
- `to_proto()` отвечает только за преобразование модели, а stub — за передачу
  protobuf-сообщения по сети;
- успешный транспортный статус ещё не заменяет проверку содержимого ответа.

## Публичный C++ API

Создать библиотеку клиента с небольшим интерфейсом, не заставляющим `main.cpp`
работать со сгенерированными protobuf-классами напрямую:

```cpp
namespace guardian::agent {

struct SubmitResult {
    bool accepted{false};
    std::string event_id;
    std::string error_message;
};

class TelemetryClient {
public:
    explicit TelemetryClient(std::shared_ptr<grpc::Channel> channel);

    [[nodiscard]] SubmitResult submit(
        const guardian::model::TelemetryEvent& event,
        std::chrono::milliseconds timeout);
};

}  // namespace guardian::agent
```

Допускается эквивалентное представление результата, если оно сохраняет три
важных состояния: успех, ID принятого события и безопасное описание ошибки.

## Поведение `submit()`

1. Проверить входное событие посредством существующей модели и `to_proto()`.
2. При локально некорректном событии не выполнять сетевой вызов.
3. Создать новый `grpc::ClientContext` для каждого вызова.
4. Установить deadline относительно текущего времени; CLI использует 3 секунды.
5. Вызвать синхронный `SubmitTelemetry` у сгенерированного stub.
6. При `grpc::Status::OK` проверить непустой `event_id` и вернуть успех.
7. При ошибке вернуть пользователю код/сообщение без аварийного завершения.

Объект клиента может переиспользовать channel и stub, но `ClientContext` нельзя
переиспользовать между вызовами.

## Точка входа и CLI

`guardian-agent` должен поддерживать:

```text
guardian-agent [--server HOST:PORT]
guardian-agent --help
guardian-agent --version
```

- адрес по умолчанию: `127.0.0.1:50051`;
- `--help` и `--version` не выполняют RPC;
- обычный запуск создаёт одно корректное синтетическое CPU-событие;
- ID события и устройства должны быть непустыми и уникальными в пределах
  процесса; для MVP достаточно сочетания времени и фиксированного префикса;
- при успехе вывести `Telemetry accepted: <event_id>` и завершиться с кодом 0;
- при недоступном сервере, timeout или отклонении события вывести понятную ошибку
  в `stderr` и завершиться с ненулевым кодом;
- бесконечный цикл, Windows Service и фоновая отправка пока не нужны.

## Файлы и CMake-targets

Предлагаемая структура:

```text
agent/include/guardian/agent/telemetry_client.hpp
agent/src/telemetry_client.cpp
agent/src/main.cpp
tests/agent/telemetry_client_test.cpp
```

- создать библиотеку `guardian-agent-client` и alias `Guardian::AgentClient`;
- библиотека связывается с `Guardian::Common`, `Guardian::Proto` и
  `Guardian::Rpc`;
- `guardian-agent` связывается с `Guardian::AgentClient`;
- публичные include-пути задаются на уровне target;
- предупреждения проекта остаются включёнными;
- сгенерированные protobuf/gRPC-файлы по-прежнему находятся только в build.

## Тесты

Обязательные проверки:

1. корректное CPU-событие проходит через реальный loopback gRPC-сервер;
2. клиент получает тот же `event_id`, который отправил;
3. локально некорректное событие отклоняется до RPC;
4. серверный `INVALID_ARGUMENT` превращается в неуспешный `SubmitResult`;
5. недоступный loopback-адрес или истёкший deadline не зависает и возвращает
   ошибку;
6. `guardian-agent --help` завершается с кодом 0;
7. `guardian-agent --version` печатает версию и завершается с кодом 0;
8. весь существующий CTest остаётся зелёным.

Сетевые тесты должны использовать loopback и автоматически выбранный свободный
порт. Они не должны зависеть от внешней сети или уже запущенного вручную сервера.

## Последовательность реализации

1. Добавить публичный интерфейс и CMake-target клиентской библиотеки.
2. Реализовать преобразование результата и deadline в `TelemetryClient`.
3. Написать тесты библиотеки с локальным тестовым gRPC-сервером.
4. Обновить `guardian-agent` и разобрать CLI-параметры.
5. Добавить CLI-тесты в CTest.
6. Собрать `guardian-server` и `guardian-agent` на Windows/MSVC.
7. Запустить полный CTest.
8. Вручную запустить сервер, затем агент и увидеть подтверждённый ID.
9. Обновить README и статус ТЗ.

## Критерии готовности

- один запуск агента отправляет одно событие работающему серверу;
- сервер логирует принятие, а агент показывает подтверждённый event ID;
- недоступный сервер не приводит к бесконечному ожиданию;
- доменная модель не зависит от gRPC и Protobuf;
- сетевой код изолирован от CLI в отдельной библиотеке;
- ошибки приводят к предсказуемым exit code и сообщениям;
- все автоматические тесты проходят на Windows/MSVC;
- README содержит команды совместного запуска двух процессов.

## Не входит в задачу

- получение реальных CPU/RAM-метрик;
- периодическая отправка и фоновый поток;
- очередь, повторные попытки и сохранение событий на диск;
- Windows Service, установщик и автозапуск;
- TLS, токены и аутентификация;
- streaming RPC;
- удалённый публичный сервер.

## Ручная приёмка

В первом PowerShell:

```powershell
./build/server/Debug/guardian-server.exe
```

Во втором PowerShell:

```powershell
./build/agent/Debug/guardian-agent.exe
```

Ожидается, что агент завершится с кодом 0 и напечатает подтверждённый event ID,
а сервер останется запущенным и выведет диагностическую запись о принятии того же
события.
