# IPC-001 — Локальная граница Agent ↔ Desktop

## Статус

Реализована на Windows/MSVC. Серверный и Qt-интеграционный тесты проверяют обмен,
частичные данные, ошибочные запросы, disconnect и автоматический reconnect.
Ручная приёмка двух реальных процессов остаётся в release-checklist.

## Цель

Сделать `guardian-agent` единственным владельцем Windows collectors. Desktop не
должен повторно обращаться к WinAPI: он получает последний снимок CPU/RAM от
работающего Agent через защищённый локальный IPC.

После этапа компоненты работают так:

```text
WinAPI collectors → TelemetryRunner → LatestSnapshotStore
                         │                    │
                         │                    └→ Named Pipe → Qt Desktop
                         └→ gRPC → Guardian Server
```

Недоступность удалённого gRPC-сервера не должна запрещать GUI читать последний
успешно собранный локальный снимок.

## Учебная цель

В ходе этапа нужно разобраться:

- зачем разделять процессы и назначать одному процессу владельца данных;
- чем IPC отличается от сетевого API;
- как работает Windows Named Pipe;
- зачем потоку байтов нужен framing;
- как Protobuf используется поверх произвольного транспорта;
- как синхронизировать доступ к общим данным между потоками;
- как GUI переживает запуск, остановку и перезапуск фонового процесса.

## Принятые технические решения

### Транспорт

На Windows используется Named Pipe с логическим именем:

```text
ai_pc_guardian_v1
```

Нативное имя:

```text
\\.\pipe\ai_pc_guardian_v1
```

Agent создаёт сервер через WinAPI. Desktop подключается асинхронно через
`QLocalSocket` из модуля Qt Network. Qt не добавляется в зависимости фонового
Agent.

Loopback TCP для этого этапа не используется: локальный pipe не занимает порт и
позволяет ограничить доступ средствами Windows ACL.

### Модель взаимодействия

IPC является read-only со стороны GUI:

1. Desktop подключается к Agent.
2. Desktop отправляет `LocalSnapshotRequest`.
3. Agent отвечает `LocalSnapshotResponse` с последним известным снимком.
4. Соединение остаётся открытым для следующих запросов.
5. При разрыве Desktop переходит в состояние `Agent недоступен` и пробует
   подключиться повторно.

В `IPC-001` GUI не может запускать команды, менять настройки или управлять
процессами через pipe.

## IPC-контракт

Создать файл:

```text
proto/guardian/v1/local_agent.proto
```

Контракт должен содержать:

```proto
syntax = "proto3";

package guardian.v1;

import "guardian/v1/telemetry.proto";

enum AgentState {
  AGENT_STATE_UNSPECIFIED = 0;
  AGENT_STATE_STARTING = 1;
  AGENT_STATE_RUNNING = 2;
  AGENT_STATE_DEGRADED = 3;
}

message LocalSnapshotRequest {
  uint32 protocol_version = 1;
}

message MetricSnapshot {
  int64 collected_at_unix_ms = 1;
  CpuMetric cpu = 10;
  MemoryMetric memory = 11;
}

message LocalSnapshotResponse {
  uint32 protocol_version = 1;
  AgentState agent_state = 2;
  MetricSnapshot snapshot = 3;
  string status_message = 4;
}
```

Версия первого протокола равна `1`. Нулевой или неизвестный номер версии
отклоняется с разрывом соединения и диагностическим сообщением в логе Agent.

Отсутствие `cpu`, `memory` или всего `snapshot` является допустимым состоянием и
означает, что соответствующее измерение ещё не получено или завершилось ошибкой.

## Framing

Named Pipe передаёт поток байтов, поэтому каждое protobuf-сообщение оформляется
как frame:

```text
4 байта длины payload, uint32 little-endian
N байт сериализованного protobuf payload
```

Правила:

- максимальный payload — 1 МиБ;
- нулевая и превышающая лимит длина отклоняется;
- частичные `ReadFile`/`readyRead` должны корректно накапливаться;
- один read не считается равным одному сообщению;
- повреждённый Protobuf не должен завершать процесс Agent или Desktop;
- в одном соединении разрешена последовательность нескольких frames.

Код framing не должен зависеть от Qt или WinAPI, чтобы его можно было проверять
обычными unit-тестами.

## Изменения Agent

### Последний снимок

Добавить потокобезопасное хранилище `LatestSnapshotStore`, содержащее:

- timestamp фактического сбора;
- `std::optional<CpuMetric>`;
- `std::optional<MemoryMetric>`;
- последнюю ошибку сбора;
- состояние последней отправки на gRPC-сервер для диагностического текста.

Доступ синхронизируется через `std::mutex`. Метод чтения возвращает копию снимка
и не оставляет mutex заблокированным во время сериализации или записи в pipe.

`TelemetryRunner::run_once()` обновляет store сразу после сбора метрик, до
потенциально долгих gRPC-вызовов. Ошибка удалённой отправки не уничтожает успешно
собранные локальные значения.

### Pipe server

Добавить `LocalIpcServer`, который:

- запускается до основного цикла Runner;
- обслуживается отдельным управляемым потоком;
- читает только `LocalSnapshotRequest`;
- формирует ответ из `LatestSnapshotStore`;
- корректно переживает отключение и повторное подключение Desktop;
- прекращает ожидание и присоединяет поток при остановке Agent;
- не использует detached threads;
- не завершает весь Agent из-за ошибки одного IPC-клиента.

Режим `--once` не запускает постоянный IPC server.

## Изменения Desktop

Добавить `LocalAgentClient` на основе `QLocalSocket`.

Клиент должен быть полностью асинхронным: в UI-потоке запрещены блокирующие
`waitForConnected`, `waitForReadyRead` и циклы ожидания.

Состояния клиента:

```text
Disconnected → Connecting → Connected
       ↑                         │
       └──────── error ──────────┘
```

Повторное подключение выполняется с задержками `0.5, 1, 2, 5` секунд и далее не
чаще одного раза в 5 секунд. Одновременно разрешена только одна попытка.

`SystemMetricsViewModel` перестаёт:

- подключать `Guardian::WindowsCollectors`;
- вызывать `collect_cpu_metric()` и `collect_memory_metric()`;
- использовать `QtConcurrent` для локального сбора.

Вместо этого ViewModel отображает ответы `LocalAgentClient` и состояния:

- `Подключение к Agent...`;
- `Agent недоступен`;
- `Ожидание первого измерения`;
- `Система под наблюдением`;
- понятное частичное состояние, если доступна только CPU или RAM.

Кнопка обновления запрашивает текущий снимок, но не запускает новый сбор WinAPI.
Автоматический запрос выполняется раз в три секунды.

При потере соединения последнее значение разрешено оставить на экране, но оно
помечается как устаревшее и не выдаётся за новое измерение.

## Безопасность

Pipe создаётся с явным security descriptor:

- полный доступ получает текущий Windows-пользователь Agent;
- разрешается `LocalSystem` для будущего перехода к Windows Service;
- доступ `Everyone` и `Anonymous` не выдаётся;
- удалённые клиенты запрещаются через `PIPE_REJECT_REMOTE_CLIENTS`;
- используется `FILE_FLAG_FIRST_PIPE_INSTANCE`, чтобы посторонний процесс не
  занял ожидаемое имя до запуска Agent.

Все входные размеры и версия протокола проверяются до выделения больших буферов.
IPC остаётся каналом чтения: добавление команд потребует отдельного ТЗ и отдельной
модели авторизации.

## Предполагаемые CMake-targets

- `Guardian::LocalIpcProtocol` — protobuf-контракт и framing;
- `Guardian::AgentIpcServer` — Windows Named Pipe server;
- `guardian-desktop` — Qt-клиент, дополнительно зависит от `Qt6::Network`.

После этапа `guardian-desktop` больше не зависит от
`Guardian::WindowsCollectors` и `Qt6::Concurrent`.

## Обработка ошибок

- Agent отсутствует: GUI продолжает работать и показывает недоступность.
- Agent появился позже: GUI подключается без перезапуска.
- Agent перезапущен: GUI обнаруживает разрыв и подключается снова.
- Первый снимок ещё не готов: возвращается `STARTING` без выдуманных нулевых
  метрик.
- Сбор одной метрики не удался: вторая остаётся доступной.
- gRPC-сервер недоступен: локальный снимок всё равно возвращается.
- Повреждённый frame: соединение закрывается, процессы продолжают работу.
- Ответ старше допустимого интервала: GUI помечает его устаревшим.

## Тесты

### Unit-тесты протокола

- кодирование и декодирование frame;
- несколько frames в одном буфере;
- frame, разбитый на несколько чтений;
- нулевая длина, payload больше 1 МиБ и повреждённый Protobuf;
- несовместимая версия протокола.

### Unit-тесты Agent

- пустой `LatestSnapshotStore`;
- публикация полного и частичного снимка;
- чтение копии из другого потока;
- ошибка gRPC не удаляет локальные метрики.

### Интеграционные тесты Windows

- запуск pipe server с уникальным тестовым именем;
- подключение, запрос и корректный ответ;
- отключение клиента и повторное подключение;
- штатная остановка server во время ожидания клиента;
- отклонение некорректного frame без падения процесса.

### Desktop-тесты

- переходы `Disconnected/Connecting/Connected`;
- применение полного и частичного снимка;
- сохранение последнего значения после disconnect;
- reconnect не создаёт параллельные подключения.

Все существующие тесты должны продолжать проходить. После реализации проект
содержит 18 CTest-сценариев.

## Фактическая реализация

- `Guardian::Ipc` кодирует и разбирает length-prefixed frames без зависимости от
  Qt и WinAPI;
- `Guardian::AgentIpcServer` читает несколько запросов в одном соединении,
  отвечает состояниями `STARTING`, `RUNNING` и `DEGRADED` и переживает ошибку
  отдельного клиента;
- `LocalAgentClient` использует только сигналы `QLocalSocket` и таймеры Qt,
  запрашивает snapshot раз в три секунды и переподключается с backoff;
- `SystemMetricsViewModel` больше не зависит от Windows collectors и сохраняет
  последнее значение при disconnect, помечая его как устаревшее;
- snapshot старше 15 секунд считается устаревшим;
- security descriptor выдаёт полный доступ `LocalSystem` и владельцу pipe,
  удалённые клиенты и захват имени второй первой инстанцией запрещены.

Фактические CMake-targets: `Guardian::Ipc`, `Guardian::AgentIpcServer`,
`guardian_proto_messages` и `guardian-desktop` с `Qt6::Network`.

## Ручная приёмка

1. Запустить `guardian-agent` и `guardian-desktop`.
2. Убедиться, что CPU/RAM меняются, а Desktop не вызывает collectors напрямую.
3. Остановить Agent: GUI должен показать `Agent недоступен` и не закрыться.
4. Запустить Agent снова: GUI должен восстановить соединение самостоятельно.
5. Остановить удалённый gRPC-сервер: локальные данные должны оставаться доступны.
6. Закрыть GUI: Agent должен продолжить работу.
7. Проверить штатную остановку Agent без зависшего IPC-потока.

## Критерии готовности

- Agent является единственным владельцем WinAPI collectors;
- Desktop получает реальные CPU/RAM только через Named Pipe;
- UI-поток не блокируется ожиданием IPC;
- disconnect и reconnect проверены;
- pipe закрыт от посторонних локальных и удалённых клиентов в пределах принятой
  модели запуска от текущего пользователя;
- ошибки IPC не завершают Agent или Desktop;
- сборка, `qmllint` и все тесты проходят;
- README и статус задачи обновлены в том же коммите.

## Не входит в задачу

- запуск Agent как Windows Service;
- автозапуск, tray и установщик;
- SQLite, история и offline queue;
- удалённый IPC или открытие локального pipe в сеть;
- команды управления компьютером;
- диагностика причин и генерация советов;
- AI, OpenRouter, биллинг и prompt-injection protection.

Эти возможности добавляются отдельными этапами после формирования стабильной
локальной границы Agent ↔ Desktop.
